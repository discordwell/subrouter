# Known issues (condensed)

Problems, gotchas, and meters that mislead, each with its status. A heading that starts with "Before §N" describes a build older than that `PATCHES.md` section. This copy is condensed.

## Fixed here, still open upstream: the router refuses traffic while every account has quota

Symptom: `no non-exhausted claude accounts available` while `sr claude list` shows accounts at 100% headroom. Fixed by §9. Upstream still has it, so a rebase onto newer `manaflow-ai/subrouter` reintroduces it unless §9 is ported. It presents as a quota problem but is not one.

Cause: the usage sweep (default 10m, `GET https://api.anthropic.com/api/oauth/usage`) returned `401 Unauthorized` for every Claude OAuth account on every cycle. The sweep was codex-shaped: the auto-switch loop's default `FetchScores` and the startup fetch looked accounts up in the Codex store and hit the Codex endpoint, where Claude tokens are invalid. With no usage data the scheduler scored every Claude account exhausted, and the pick-then-refuse check in `accountForSessionProviderWithOptions` returned a 503.

`sr claude list` and `/_subrouter/usage-status` read rate-limit headers from real proxied responses (`usageWindowsFromFableHeaders`), a separate path. A healthy `sr claude list` is not evidence the scheduler can see anything.

Pick-then-refuse is kept on purpose: it is correct once scores are honest. The code refuses to reject on the softer `UsableForNewSession` signal, because stale scores there caused bogus 503s. Fable has a real fallback instead of a refusal (§11). If the error returns, ask what the sweep is failing at, and look for `account score` lines reading zero (restored for this diagnosis). Workaround on unpatched upstream: `subrouter serve --fetch-usage=false` (cost: no headroom-aware selection and no auto-switch).

## Rolling back the binary is more dangerous than rolling forward

Putting the old binary back re-arms a pool-wide brick. Capture `~/Library/Logs/subrouter.err.log*` (since PATCHES §39 that includes rotated copies `.1` to `.3`, which hold the pre-deploy history) and fix forward. Forward is safe: later guards only refuse to start on states that were already broken, and say why. Three one-way doors:

Without PATCHES §7 (keychain payload compaction): the old binary writes indented JSON, `security -w` hex-encodes multi-line payloads, and every pooled Claude credential becomes unreadable after its first token refresh (§7, across 100% of the pool). Without PATCHES §5 (`SaveConfig` stopped minting): a `cloud.json` recovery path can re-mint `localProxyToken`, desyncing it from the `ANTHROPIC_AUTH_TOKEN` in `~/.claude/settings.json` that every client uses. Those two values must stay byte-identical.

Older than the 2026-09 upstream merge (Codex credential isolation, §23): once Codex records are attested or re-logged, a pre-merge binary writes a pool chain back into `~/.codex/auth.json` at start or within one interval. Each refresh it makes also erases `oauthCredentialOrigin`, so the next upgrade refuses those accounts again. The box's deploy script, `deploy-laptop.sh` and `rollback-laptop-peer.sh` refuse that restore unless `ALLOW_PRE_ISOLATION_ROLLBACK=1`.

## `/ready` stays 503 and stores reload every 5 s while no Codex record can be scored

Upstream wiring from the 2026-09 merge. With auto-switch on (`--sr-switch-interval` > 0, as we deploy) and Codex OAuth records present, `/_subrouter/ready` answers 503 `{"startup_ready":false}` until one Codex sweep produces a fresh score. A failed sweep retries every 5 s (`sr_startup_scores.go`), unbounded. Each retry calls `RefreshAccounts`, which re-reads every store (each Claude profile's keychain on macOS) and bumps the account generation, discarding any score publication that spans the bump, the Claude startup fetch included.

It lasts until the Codex records are attested or re-logged after the upgrade, or recurs when the machine's only Codex account dies. Fix: finish the migration or remove the dead record; with no Codex OAuth record `/ready` is 200 at once. `/_subrouter/health` stays 200 throughout, so poll health to tell "up" from "scored".

## From the provider-first fold to §19, re-auth Claude only with `sr add local claude`

On those builds, the provider-first fold turned `sr claude login main` into `sr login claude main`, the cmux.com sign-in, which ignores the name and rewrites `cloud.json`. On the same builds, a machine with a default server answers `sr add claude <name>` and `sr claude add <name>` with a refusal pointing at `sr add <server> claude <name>`, which moves the account off the machine. Fixed by PATCHES §19. Until a machine carries that build, use `sr add local claude <name>`. On a build with the §22 grammar pass, OAuth re-auth is `sr claude addr <name>`, and `sr claude add <name>` mints a one-year setup token. Delete this entry once no machine runs those builds.

## Gotcha: `opus-weekly` reads 0% because it is synthesized, not measured (pre-§24 builds)

On a daemon older than §24, `/_subrouter/usage-status` shows `opus-weekly` and `sonnet-weekly` on every Claude account whose usage fetch succeeded. When Anthropic's response has no opus bucket (normal, since Opus has no limit of its own), that build appends a 0%-used placeholder, so 0% means "no data", not "unspent". Opus use lands in the general `7d` bucket. The only independent meter is Fable's (the usage answer's `limits[]` Fable row since §64, else `seven_day_oauth_apps`; upstream header `anthropic-ratelimit-unified-7d_oi-utilization`).

The placeholder existed only on the usage-endpoint path. So a one-year setup token, or an OAuth account whose usage fetch failed while the probe answered, had no Opus/Sonnet pool, and `ForModel` zero-filled it out of Opus and Sonnet routing. §24 removes the placeholder and routes a model with no separate limit on the account's `5h`/`7d`. Delete once no machine runs a pre-§24 build.

## A spent pool used to roll back a healthy laptop build

Fixed in `deploy-laptop.sh`. `verify()` probed `POST /v1/messages` and failed on 404 or 000. With `SUBROUTER_ALLOW_LOOPBACK_PROXY=1` the probe skips the token gate, so it is a real upstream request that walks the retry chain. With the weekly overage allowance gone, every account 429s, the chain outlives `curl -m 10`, and curl reports 000, the same code as a missing route, so the deploy rolled back. To prove the probe is at fault, run the same `--check` against the already-deployed binary (on 2026-09-16 it failed 3 of 3 runs, having passed twice hours earlier with no swap).

`srq pool` said nearly every local Claude account had headroom while all 429d: it read `5h`/`7d`, but the binding meter was `anthropic-ratelimit-unified-7d_oi`. Fixed in `srq` (PATCHES §40): Claude rows show `fable=` (`oauth-apps-weekly`), a spent one is flagged `FABLE-REFUSED`, and the header ends `!! Fable 0/N: no account takes a new Fable session`. The lead count is now the daemon's new-session verdict, which also ignores the Fable meter and would still say 10/10, so read the Fable part of the header. The identity probe also needs one usable account, so a spent pool failed two checks at once.

## Targeted peer forwards (PATCHES §31): known gaps

The answering daemon serves a peer's named account or refuses it (`409` + `X-Subrouter-Target-Refused`, `internal/proxy/target_placement.go`). Gaps:

Mid-socket Codex quota failover commits the local alternate and tells the client to reconnect (1013), since an open websocket has no turn to forward. The session is marked (`markForcedRerank`, 5 min) and the reconnect is the forced re-rank across every pool. A client that does not reconnect within 5 minutes keeps the local alternate as an ordinary pin. The decider reads the request's pool verdict (`normalized.pools[k]`'s `new_session`) when present. A peer that publishes no pools is judged on its account-wide verdict, and a spent Fable pool shows up as the request-time refusal, which recomputes.

A dead credential found by the request-time refresh (`invalid_grant`) refuses after the pin is written: `409 auth_invalid`, nothing sent upstream, no substitute, and the account is marked exhausted. The stale pin is harmless, but "refused before any session-store write" holds only for scheduler-derived reasons. A Codex `usage_limit_reached` 429 is recognized by peeking the error body; a body over 1 MiB reads as transient for one turn and refuses on the next.

On 2026-09-27 the laptop's local sweep was cut (`local_known=false`), a bug in the deciding daemon mostly fixed by §34 (34.2, 34.3). Since then, for an account whose keychain answered within the minute, neither a sweep refresh nor the sweep's pre-read waits on a profile's locks or runs `security`, and no refresh waits on another profile's lock through `ClaudeConfigDir`'s shared history lock. A turn sent to the peer because its refresh reached no verdict logs that account with `local_cause`, and `local_failed_over_from` when it was a failover candidate. The rest is in "Residual gaps §34 leaves open". A peer account's debit counts only this daemon's targeted turns; other deciders' and the peer's own traffic appear only in its next usage body. With one decider this is the whole draw. Only a Codex model-unsupported 400 is stamped `X-Subrouter-Target-Refused: model_unsupported`; a Kimi capability failure on a target is not stamped and would reach the client (no Kimi peer exists today).

The switch table's rows for a bare `ErrCredentialUnchecked` or a silent store (classed transient) have no production caller today: the request path wraps both as `errRefreshTransient`, and the sweep publishes them as `sweep_cut`. The rows exist so the next caller does not read it as a dead login. A targeted Codex turn runs the same-account capacity ladder (bounded at 10s, under the decider's 30s header timeout) and a failure past it is stamped `X-Subrouter-Transient: overload`, so the hold is kept. It does not mark the account (a mark steers a switch, and the targeted account is the decider's to move), so the box's placement does not learn from it. A peer that served through the transport-level stage is stamped `X-Subrouter-Pool: local` with no `X-Subrouter-Peer`; the hold, `/_subrouter/sessions` and the `local pool exhausted; served from remote pool` line name the peer and account.

## Before §28: a slow keychain reads as a dead login and moves warm sessions

Fixed by PATCHES §28 for laptop builds before it (the moves stick only from §25). The box is unaffected: it reads credential files and has no vault. Under load the log shows `account reload refresh failed account=X error="Claude profile \"X\" has no access token"` for a healthy account, then `rerouting cold sticky session ... evicted=true exhausted=true` and `session moved to another account; upstream prompt cache is cold`, while usage-status shows `auth_valid=true`. The same text means a real dead login. Cause: a `security` read cut by the 5 s pool budget or its own 5 s clock was treated as "no keychain item", and the zeroed headroom was carried into the next sweep's seed.

After §28 a store that stays broken reads as a dead login on purpose. Immediate verdicts: on the box, a credentials file or lock (`<instance>.credentials.lock`, `<instance>.refresh.lock`) that is root-owned 0600, a directory, a loop, or a path through a file. A silent store becomes a verdict after 15 minutes of sustained silence (at least 3 reads, none cut by a deadline, no two counted failures more than 12 minutes apart; since §34 counted from the first failure that was not a hang), or after 1 hour of any silence. A locked login keychain (the laptop case) logs `error="no access token can be read: ..."`, and the first time a profile passes the bound, one ERROR line `Claude credential store has not answered`.

Before the verdict, from its first unanswered read, the account is not offered to new sessions, except that a streak of `security` hangs alone does not count (load produces those), and the silent account is offered when every answering account is spent or in holdout. Warm sessions keep it, and each turn answers a marked 502 until the store answers. Fix the store (`chown subrouter:` on the box, or unlock the keychain); the account returns at its next answering read with no hold. If a reload dropped it while broken, it returns at the next reload, a restart, or the next `/_subrouter/usage-status` sweep in which it answers. A profile unanswered at startup is listed without a credential, not dropped.

Fixed in §34 (34.1): on 2026-09-27 between 17:41 and 17:44, four keychain writes logged `write Claude credential to keychain: signal: killed` (`securityKeychain.write` has a 5 s clock inside the 10 s persist clock), and two accounts went `invalid_grant` because the rotated refresh token never landed. Now the `-U` upsert retries on the persist clock, a rotation the keychain refuses goes to `.credentials.json` as a stand-in, a persist that cannot take the lock retries then writes `.credentials.rescued.json` for the next read to adopt, and a re-read with nothing to compare writes the rotation. A retry that lands logs only a Warn with `instance=`. The stand-in, the rescue and each remaining way to lose a rotation log one ERROR naming the profile.

Still open: when `.credentials.json` reads and the keychain read gets no answer, `readCredential` drops the keychain error and the file wins. If the file is older with an expired access token, its refresh token may already be rotated, giving a terminal `invalid_grant` that moves sessions. Latent: only eleven-alpha has a file on the laptop, and it goes live when a profile with a file is re-authed in place (a §34 stand-in is exposed while it lasts). Candidate fix, not done: return the keychain error when the file needs a refresh and the keychain read was unchecked. Spot it as `invalid_grant` right after `credential not checked` on a profile with both a file and a keychain item.

## Before §35: Codex moves on a burst 429, lapsed Codex accounts go unmarked, on-hold accounts 503 or go to the peer

Fixed by PATCHES §35. Affects builds before it: the Codex issues on any daemon serving Codex over HTTP, the on-hold issue on any daemon holding a Claude OAuth account. ## Residual gaps §45 leaves open (CI and test isolation)

Upstream's flake and speed series (#385, #404, #415, #419 to #421) is not ported, nor is the fix for our `TestClaudeSettingsGuardianRemovesFileAfterLauncherSIGKILL` create-then-write race.

## Before §41: draining accounts queue behind the earliest roll under a quarter-step taper

The usage endpoint rate-limits per login. Two reads of `/api/oauth/usage?cedar_ember=1&skip_spend=1` seconds apart drew `429 rate_limit_error: Rate limited. Please try again later` on 2026-09-29, failing the first two claims, and a read about two minutes later succeeded. Since §46.7 a claim uses the sweep's cached block when it is under 30 minutes old, and waits out any 429 (`Retry-After`, else 30 s, 60 s, 90 s) inside 4 minutes, resending with the same request_id, and it says how long it waited. A second claim inside the `cooldown_until` window was not tried.

Deploy the holding daemon before the CLI. The one-call `sr claude reset` sends no `expected_organization`, so a §46.5 daemon answers 400 ("must carry expected_organization from a preview") and the CLI says the holding daemon runs an older build. Nothing is claimed. Redeploy the box (or restart this machine's daemon) first.

Unverified: the sweep asks `?cedar_ember=1` without `skip_spend=1` (it needs `spend`), which Claude Code never sends. If that returns `cedar_ember: null`, the daemon reads the block with `?cedar_ember=1&skip_spend=1` in the background at most once an hour per account, so the column may be up to an hour stale. The owner should confirm the combination with one read-only GET. A claim takes the grant from that cached block only when it is under 30 minutes old and offers a claimable `next_grant_id`. A cached refusal is re-read live, Anthropic's POST answer decides, and a block read before the account's last claim POST or with another token (new login or refresh since) is never used.

The request shape is copied from the 2.1.284 binary and observed working once, not captured on the wire. An `unavailable` answer (`stamp_indeterminate`, `reset_unconfirmed`, or an unknown result) means the claim may have landed. The daemon keeps the request_id for a retry within 10 minutes, in memory only. Check with `sr claude reset <name> --dry-run` before retrying: it never uses a block read before the claim.

## §43.2 and §46.8: the public admin path from `sr`, and Codex anytime

What `sr` over the public admin path (§43.2) leaves open:

- **A named admin token lives on the laptop and crosses the internet.** It sits in `servers.json` (0600) as `publicAdminToken` and travels over TLS pinned to the box's certificate. Leaked, it opens every public admin route from anywhere until revoked or expired (PATCHES §43.2). Renew before `EXPIRES`: a lapsed token 401s and `sr` names the fix.
- **It is full admin on the private listener too**, `transcripts` included, to anyone reaching `:31415`, flag or not. Turning public admin off does not revoke it.
- **Every active admin-role token on the box becomes public with the flag.** The enable procedure audits them first. Nothing enforces it.
- **Account credentials can cross the internet.** With the tailnet down, `sr claude move`, `push` and `server sync` upload through the public listener, pinned. `SR_STATUS_SERVERS` does not gate it. `sr server set-public <name> --clear` keeps imports on the tailnet.
- **A leaked token can spend every Claude account's one saved reset (§46.9)**, since `claude-reset` is on the public listener with the flag. Calls log `admin request by access token caller=<name> ... listener=public`, and each claim POST logs `claude reset claim sending` at WARN. Mitigate with `subrouter token revoke <name>` on the box. A spent reset does not come back.
- **A leaked token can spend Codex credits early.** The daemon honours `anytime=true` (§46.8) from any admin credential, public listener included, logging `WARN codex reset credit redeem anytime caller=<name> listener=…`. Refusing `anytime` on the public listener is an owner decision not yet taken.
- **The fallback is only for an unreachable private URL.** A tailnet connection that opens then stalls is an error, not a fallback, because the request may have gone out. A private dial is capped at 2 s when a public path stands behind it, so a tailnet slower to connect uses the public path.
- **A pin mismatch may be an impersonator, and nothing is sent.** Take the new pin only on the box over the tailnet (`subrouter fingerprint`), never from the endpoint, then `sr server set-public <name> --fingerprint <pin> --keep-token`. A new box or reassigned address needs a new token too: `set-public` refuses to carry the stored one to a new URL or pin without `--keep-token`.
- **The Python tools do not fall back.** `sr-plot`, `srdash` and `claudemode` dial `url` only.

`sr codex reset` redeems anytime (§46.8), not verified live. No credit has been spent on a Codex account below its weekly limit, so whether ChatGPT's consume endpoint then resets, refuses, or spends the credit for nothing is unobserved. The daemon reports the answer verbatim and the line says it was early. Credits are finite, so the verb now spends one on an account that did not need it. Only the verb sends `anytime` (a CLI convention), but the daemon accepts it from any admin credential. A pre-§46.8 holding daemon ignores `anytime` and refuses as before, and the verb says to deploy it.

## Superset's terminal daemon outlives a logout; its shells lose Keychain, TLS, launchd (§47)

Measured 2026-09-30 with Superset 1.32.0 (bundled pty-daemon 0.3.5). `pty-daemon.js` survives a macOS logout and the app **adopts** it at the next login, so every Superset terminal, old tab or new, is a shell in the ended login's launchd bootstrap namespace. A tmux or screen server started before a logout does the same. In such a shell the user lookup fails (`user: unknown userid 502`, `id -un` prints the uid), `security` cannot create a keychain search (-50, then exit 44, read as "item not found"), Go 1.26's TLS verifier fails every handshake with `x509: OSStatus -26276`, `launchctl managername` exits 153, and `print` exits 141 `Reentrancy avoided` for every label. The subrouter daemon, a launchd job of the current login, is fine. How this broke `sr` and the deploy scripts, and the fix, is PATCHES.md §47.

How to tell: `launchctl managername` exits 153 (`Could not get manager name.`), where a current GUI login prints `Aqua`. On a §47 build `sr doctor` opens with `FAIL  login session`, `sr status` heads its table with `read from its daemon`, other verbs exit 2 with `refused: this shell belongs to a macOS login session that has ended`, and `bin/sr-triage` prints a `session:` line. Do not use `TERM_PROGRAM`: Superset sets `TERM_PROGRAM=kitty` and `TERM_PROGRAM_VERSION=0.42.0` on purpose. Its own variables are `SUPERSET_TERMINAL_ID` and `SUPERSET_HOME_DIR`, and `$SUPERSET_HOME_DIR/host/$SUPERSET_ORGANIZATION_ID/pty-daemon-manifest.json` has the daemon's `pid` and `startedAt`. A daemon started before your last login is the cause.

`gh` working proves nothing. `gh` 2.101.0 is built with Go 1.27.1, which on macOS loads roots from disk and skips the platform verifier when `SSL_CERT_FILE` or `SSL_CERT_DIR` is set, and Superset sets `SSL_CERT_FILE=/etc/ssl/cert.pem` when unset. In the same shell `gh api user` worked and `env -u SSL_CERT_FILE gh api user` failed with `-26276`. `sr` and `subrouter` (Go 1.26.5) ignore `SSL_CERT_FILE` on macOS. curl and node use their own CA stores and work. None of this reaches the Keychain or launchd.

Superset's own guard did not fire. Its daemon probes trustd (`security verify-cert` on the first certificate in `/etc/ssl/cert.pem`) once at daemon start and reports that in every hello. The supervisor acts only at adoption, replacing a daemon whose startup probe was unhealthy if its own probe is healthy, and by design never re-probes or kills one mid-life. The measured daemon was an auto-update handoff successor started at 02:31 in a live login, probed healthy, and was adopted by the 19:06 login still reporting `trustdHealthy: true`. Rerun from its shells, the probe exits 1 with `-26276`. The fix belongs in Superset: re-probe on hello or when host-service starts in a new login, and offer the restart. The restart closes every session, so it should ask first.

Remedy: open a new Terminal.app (or other non-Superset) window, since logout quits every app. A new Superset tab, tmux window or screen window is no way out. For tmux start a new server (`tmux -L <name>`; plain `tmux` joins the old one), for screen a new session (`screen`, not `screen -r`). Superset's Settings > Terminal > Terminal daemon > **Restart daemon** closes every Superset terminal and host-service starts a new daemon in the current login. That is a person's call: an agent never signals the daemon pid, which ends every Superset terminal (so `sr` does not print the pid). Quitting and relaunching Superset is not enough (it adopts the same daemon). "Quit Completely" stops host-service and the v1 terminal host, not the v2 pty-daemon (read from source, not run). No setting turns adoption off.

Left open (§47.7): pooled launches (`sr claude`, `sr codex`) are refused in such a shell, not served. On a team (cmux.com) credential source `sr status` still fails there with x509 (refusals point to `srq pool`). The quickstart script's `--peer` and the remote-key script's printed bootout/bootstrap have no session check. The `Aqua` answer in a live GUI terminal was not observed from the shell this was built in.

## Residual gaps §54 leaves open

- **A blip on the peer's path alone still ends every hold, by design.** §54 keeps holds only when this machine cannot tell the outage from its own offline. When local turns answer, two failed forwards to the box (box down, or its path timing out or refused, never this machine's own no-route error) set `peer_down=true` and every hold ends. That was 6 of the laptop's 14 openings in the eight days to 2026-10-09. Whether it should keep holds is an open owner question (PATCHES §54). Since PATCHES §67 such a blip keeps them until the box has answered nothing for the grace, 15 minutes by default.
- **Bystanders of a real `peer_down` rode their local placeholders.** A box-held session that did not trip the opening lost its hold with no line, and its next turn stayed on its local placeholder pin under the warm rule. A fix was deferred. Closed by PATCHES §67 (67.5): each such session's next turn re-ranks as forced, and each ended hold logs its own line.
- **The observer's blind spots.** Only `Server.transport()` and the local Codex websocket dial count as evidence, not usage sweeps, token refreshes, the Fable chain and Bedrock, the Azure Codex fallback or the Codex regional egress. A machine whose only local traffic goes those ways reads a dead box as itself offline: its first opening keeps holds (`why=no_answer`) and counts as a local failure. Holds then live until this machine comes back (a local answer with no local failure after it) and two peer requests sent since then fail, or the 70-minute bound lapses. The second request need only follow the first's seen failure, not a cooldown, because a held turn is admitted by the breaker before the X6 wait for a usage body (up to 250 ms) and dated after it. Each cooldown until then, held turns pay the dial or header bound again. A drop nothing observed, after a local answer in the outage, reads as the box down, as does the first cold link after a reboot or wake whose one failed held turn timed out offline with its fallback unobserved, in a daemon with no local failure since start.

## Residual gaps §56 leaves open

- **A box from before §56 publishes no hold.** Until it deploys, a §56 laptop ranks the box's holders at 1x and the box's verdict drains them only on their 24h roll. Nothing is misrouted; they get no priority.
- **An older laptop honours a §56 box's early burndown without the 2x.** The verdict's `burndown: true` is drained first by any laptop since §31. The 2x needs `seconds_to_held_reset_expiry`, which an older laptop ignores.
- **`SUBROUTER_RESET_HOLD_PRIORITY=0` is per daemon.** Off on the laptop alone, the laptop still drains box holders first on the box's verdict. Turn it off on the box first, then the laptop.
- **With `SUBROUTER_FABLE_RESERVATION=1` and Fable unspent, early burndown takes 2 sessions at 25% measured and 1 below about 12.5%**, because the taper reads `WeeklyHeadroom`, which carries the Fable reservation only with that switch on (§57). By default it takes the full 4/3/2/1. The drain never takes fewer than 1, so it still reaches the wall, more slowly.
- **A reserved holder may never burn down early.** The reserve gate reads `WeeklyHeadroom` (less the live debit and, with `SUBROUTER_FABLE_RESERVATION=1`, the Fable reservation), so a reserve above the holder's spendable week keeps it out.
- **The legacy peer path can keep a 2x up to a body's age past expiry.** A peer on the legacy or `ignoresTargets` path anchors published seconds at now with no body-age gate, so an hour-old last-good body keeps the 2x up to an hour past the grant's expiry. Ranking only.
- **`sr status` does not show early burndown.** Its Pick column can say `not routable` for a holder being drained. Read `srq pool` (`burndown·reset n/m`, `2x`) or the pool board.
- **In shadow mode, the default, nothing claims the reset.** An early-burndown holder stays at its wall until the owner runs `sr claude reset <name>` or the week rolls, and the daemon logs what it would claim (§93). With `SUBROUTER_AUTO_RESET=1` the daemon that holds the account claims the reset there itself, behind the owner's under-1% condition, and the account's turns wait for it on the account (§93.2). It claims only when the claim is worth making (§94.2): a holder in a pool that does not need its reset, or whose roll is too near for a claim to add a quarter of a week, is held back and stays at its wall until a later reading or wall finds the claim worth it.

## Residual gaps §57 leaves open

- **Opus and Sonnet can spend an account's whole week while its Fable meter is unspent.** With the Fable reservation off (the default since 2026-10-15), nothing keeps budget back for Fable, so Fable capacity can be stranded, which §10's reservation prevented. Accepted while no Fable model's weekly limit binds. When a new Fable ships whose limit does, set `SUBROUTER_FABLE_RESERVATION=1` on both daemons and restart them.
- **Mixed switches or versions skew the cross-pool ranking.** Each daemon publishes its own `weekly_headroom` and the laptop ranks box accounts on the box's number. A box with the reservation (pre-§57, or switch on) publishes about half its measured week for a Fable-unspent account, so the laptop ranks it at about half pace until both run the same setting. Nothing goes to a spent account; only the balance between pools is off.
- **The pool board's box rows follow this daemon's switch, not the box's**, because `schedulerFromStatuses` rescores box rows from the box's raw windows here.

## Before §58: a network blip fails every turn in flight at once

A pre-§58 daemon answers a turn whose upstream it cannot reach with an immediate 5xx: `502 upstream request failed` for a DNS failure or a refused or timed-out dial, `502 refresh selected account: account token refresh did not complete: …` when the token refresh hit the same network, or the upstream's own 500/502/503/504. Claude Code retries a few times within a minute and then gives up the turn, and a workflow agent that gives up is gone. On 2026-10-20 the laptop logged 2,410 such `/v1/messages` failures in four hours across two outages (DNS `no such host`, then `connection refused` to the gateway). Check the daemon's build before blaming the network alone: a §58 daemon logs `proxy hold is on` at start and `proxy hold started` while absorbing an outage.

## Residual gaps §58 leaves open

- **A sleeping laptop.** Nothing runs during sleep, so a hold cannot carry a turn across a closed lid, though it helps at wake while the network rejoins. A turn streaming at sleep already has bytes out and is not retried. The deadline should count awake time only (Go's monotonic clock on macOS is `mach_absolute_time`), read from source, not measured.
- **Not held:** Codex websocket turns, chunked request bodies, bodies over 128 MiB, requests a peer forwarded (the forwarding daemon holds those), and anything on the box's public :31416 listener. A direct :31416 client (a cloud test box's static-token traffic) still gets every transient failure at once.
- **A local transport failure was not sent to the peer.** A held turn retries its own placement, though in a DNS-only outage the box's IP-literal listener may still answer. Routing there was an owner decision outside §58. Closed by §59 (the outage spill) on a daemon that has it.
- **Fallback stages' 5xx are not held:** Bedrock, the Fable API key, the Opus substitute, and the peer stage inside the usage failover.
- **More log lines in an outage.** Every held attempt writes its own `proxy request failed` (and for a POST `replayable upstream request exhausted`), up to about 25 attempts per 8-minute hold. The §39 log cap bounds the file.
- **Peer breaker strikes per attempt.** A held turn that tries the peer counts a strike each time, as client retries did. §54 decides whether an opening ends holds.
- **The box needs its own deploy.** The laptop holds every turn of its own sessions without it. Once the box runs §58 it holds only turns reaching its tailnet listener directly.

## Before §59: a broken resolver holds every turn until DNS comes back

A pre-§59 daemon (with §58) holds a turn whose lookup fails and retries the same host for up to 8 minutes per client retry, even while the network carries traffic and the peer, dialed by IP, answers. On 10/20 that was 3,148 `lookup api.anthropic.com: no such host` failures between 16:00 and 01:00 CDT while the peer served 313 to 4,771 turns an hour. A §59 daemon logs `sticky dns is on` and `outage spill is on` at start.

## Residual gaps §59 leaves open

- **A lookup that answers wrongly is believed.** Only a failed lookup falls back to the remembered address. A private or hijacked answer (10/20 handed out 172.16.0.1 at times) is dialed, and when that dial fails, the spill and the hold take the turn.
- **A resolver that hangs** costs each new connection the dialer's 30 s before the remembered address is tried. A Codex websocket dial carries its 30 s handshake deadline in its context, so a lookup that hangs that long leaves no time for the fallback.
- **A blackholed upstream costs 30 s per spilled turn.** The spill keeps no "local is down" state, so each turn dials local first and waits out the dial timeout. A refused dial or failed lookup costs milliseconds.
- **The memory is not on disk.** A daemon restarted during an outage (a deploy, a crash) remembers nothing until a lookup works, and only holds and spills.
- **A remembered address that moved** within the maximum age (a week) fails TLS, and a certificate error is answered at once, not held.
- **The cap is per daemon and is not the box's only load.** Turns placed on the peer by ranking or a hold take no token, and the token refresh's one-turn serve (§20, §31) predates the spill and is not capped.
- **Side requests take tokens too.** A `count_tokens` or other side request whose local dial fails spills and takes a token, so the cap counts what the box sees. In an outage that outruns the cap, a model turn may be held while a side request went.
- **A spilled turn may land on a different peer account each turn** (ranking picks each time and no hold pins it), so its prompt cache can be cold on the peer, as any first peer turn is.
- **Codex websocket turns** get sticky DNS but are neither spilled nor held (§58).
- **Tool calls** (`ssh`, `gh`) use the system resolver and still fail during a DNS outage.

## Residual gaps §95 leaves open

- **`sr status` does not show a choice.** Read `srq pool` (`chosen week #1`, or `would choose week #1` in shadow mode) or the pool board.
- **A daemon from before §95 ignores a peer's choice.** It places new sessions on its own ranking, so only the holder's own routing loads its chosen accounts. Deploy every daemon before a holder goes to real mode.

## Residual gaps §96 leaves open

- **Two daemons can still read need differently near the bar.** Each daemon holds its own answer, so a daemon that read 1.02 holds `yes` at 0.98 while one that has read nothing above 0.98 since it started says `no`. The hold steadies each daemon's answer over time, not the pool's at one moment, and each daemon decides only for its own accounts.
- **A Claude choice keeps its old order only until 30 minutes after its gap began.** After that its order follows the value of a claim at its wall again, as every standing choice's does.
- **Need's memory is lost at a restart and at a worker swap.** The new process answers from the figures alone. An unsettled claim is not lost: its record is on disk (§93.2), and the choice reads it.
